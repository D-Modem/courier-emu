# Courier 7910: PPP login and exact IP payload (2026-11-02)

**PPP login and internet ICMP are demonstrated at 31200 V.34. V.90 still
falls back, and sustained-load reliability remains unqualified.**

## Final complete test

The fixed analog Courier 4.03 emulator dialled 7910 using the normal PCMU
transport, **without experimental level conversion**:

```
CONNECT 31200/ARQ/V34/LAPM/V42BIS
```

LCP completed, PAP authentication succeeded, and IPCP assigned:

* local/client: `10.254.104.2`;
* peer/server: `10.254.104.1`;
* advertised DNS: `10.150.150.1` (not independently queried in this test).

A stop-and-wait test returned **20/20 exact 512-byte ICMP echo payloads**:

| Destination | Sent | Exact replies |
| --- | ---: | ---: |
| PPP peer `10.254.104.1` | 14 | 14 |
| Internet `1.1.1.1` | 6 | 6 |

Each payload cycles through all 256 octet values twice, with a sequence-dependent
offset. Validation checks identifier, sequence, source IP, IPv4 and ICMP
checksums, and complete payload equality. This exercises 10,240 application
payload bytes in each direction, not merely printable terminal text.

The client recorded zero PPP FCS errors. The peer's independent journal reports
PAP acceptance of `courier-test`, the matching address pair, and **10,800 IP bytes
sent and received**: exactly 20 × (512 payload + 28 IP/ICMP header bytes).
Its hangup followed the test's deliberate stop. This establishes actual PPP
session and IP traffic, not just repeated LCP requests.

The bounded run exited 0 after 107.30 s and 364,154,943 guest instructions,
with `stop-requested` after all echoes returned. Carrier remained on until
shutdown. Active RX underruns/rebuffers, RTP missing/late samples, and UART
RX/TX overruns were zero. TX still reported one rebuffer and a 45.30-ms maximum
packet gap; this is not a blanket transport-conformance claim.

## Actual endpoint and authentication policy

Read-only service and journal inspection confirms this 7910 connection reaches
**MultiTech `/dev/ttyM4`**, interface `mtppp0`, through
`multitech-ppp.service` on Eicon420. The earlier BRI-answerer configuration's
`/dev/ttyds3,4` number mapping alone was not sufficient to identify the actual
PPP endpoint. No endpoint, PBX, routing, NAT or authentication configuration
was changed for these tests.

The existing `multitech-7910` peer requires PAP and has a lab wildcard entry
with an empty secret. The probe used `courier-test` with an empty password,
as permitted by that existing policy. This was not a Unix account login or
an authentication bypass. SIP credentials were retrieved remotely and passed
through stdin/environment, never embedded in test commands or logs.

## Active-input scheduling repair

The larger test exposed a real-time performance problem rather than a reason
to enlarge the receive queue. Pending serial input and the UART's `holding`
state unconditionally disabled native quiet polling, even while an online
character's wire level could not change before the next bit boundary.
Further, the start edge remains latched while INT1 is masked in data mode;
treating that masked edge as immediately actionable defeated the first repair.

`CourierMachine._serial_receive_quiet_until()` now recognizes the narrow case
of an online ROM byte already in flight, no console/command adapter work, no
UART request or TX work, and no unmasked start edge. Native elision has a hard
deadline at the **next wire bit boundary**. Byte completion, new input, pending
UART requests and unmasked edges remain cooperative. A masked edge is retained,
not cleared; enabling INT1 makes it actionable again. The existing 64-instruction
IRQ recognition cadence, DTE baud, DSP clock and receive queue limits are unchanged.

`tests/test_serial_receive_quiet.py` has **26 passing tests**, including guard
states, completion, masked-edge retention/re-enable, and equality of every
64-instruction pin observation. It passes on local and isolated Linux builds.
The focused local serial/quiet/UART/C5x selection completed **120 passed**;
this is not a full-suite claim.

This removes the reproduced backlog abort in the subsequent loaded call, but
**does not establish sustained duplex throughput**. In that test, only 25 of
60 requests reached the peer before shutdown: its journal counted 13,500 IP
bytes in each direction. Client UART counters show no overruns and all scheduled
input consumed, but that does not prove where the remaining upstream data waited
or was lost. A roughly 30-second mid-test stall remains unexplained. RX transport
loss/rebuffer counters were zero; TX had eight rebuffers and an 84.74-ms maximum
packet gap. Those aggregate TX counters do not establish the stall's cause.

## Probe and reproduction limits

The probe runs a standard-library userspace PPP client against the firmware's
normal DTE output and scheduled serial input. It does not inject decoded modem
payload, manufacture CONNECT, patch firmware, or put routes/interfaces on the
emulator host. Its PPP framing/LCP/PAP/IPCP implementation is archived from
`../modem-dsp-emu/tools/ppp.py`; a local peer-to-peer PAP/IPCP/exact-ICMP self-test
also passed.

The stock `--serial-pty` console path remains a separate performance limitation:
it failed the first attempted live harness. It is **not claimed fixed** by the
online non-console optimization, and these results are not a demonstrated
`pppd`-over-stock-PTY workflow.

Artifact `.artifact-archives/analog-sip-7910-ppp-20261102/` contains probe scripts,
the PPP implementation, focused test output, and final occupancy check. Each call
archive retains commands, reports, audio, pcap, PPP logs and results; selected
archives include the independent peer journal. `data_rx_bytes` / `data_tx_bytes`
are not populated by this ROM DTE path: the evidence is the UART byte stream,
PPP framing, checked IP payload and peer counters, not those zero-valued fields.
